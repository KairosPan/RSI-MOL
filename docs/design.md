## 1. 摘要

**要做的事。** `~/Desktop/RSI` 里现在只有一个 Lab Codex。这次再加一个 Meta Codex 和一个小的控制程序。Lab 做你给的任务。每个任务结束后，Meta 读这次运行的记录，判断 Lab 的工作方式有没有该改的地方。要改，它就在一份副本上改，让 Lab 用副本试跑，然后自己决定是否发布。发布的版本用于后面的任务。

**一圈怎么走**（对应 §6 的六步）

1. 运行：你给一个任务，控制程序用当前版本启动 Lab 做完它。
2. 观察：控制程序把这次运行存成记录。
3. 诊断：控制程序叫起 Meta。Meta 自己读记录，写出问题、依据和可能原因。依据不足就不改。
4. 改进：Meta 在 Lab 工作区的候选副本上做一个小改动。
5. 验证：Meta 请控制程序让 Lab 用候选版试跑。
6. 发布：Meta 自己决定。控制程序只核对它引用的试跑记录是真的、跑的就是这个候选版，然后切换版本。

**你已经定的**

- 先做任务之间的改进。任务进行中的巡检和修复（v2.1 的主路径）以后再加。
- 发布必须以真实的运行记录为依据；“改了”和“有收益”分开记。
- Meta 可以改整个 Lab 工作区，包括 Lab Codex 本身。它自己决定，不用你批准，也不设打分门槛。
- 四样东西 Meta 碰不到：任务的冻结要求和完成判据、已有的运行记录、执行发布和回退的程序、预算上限。
- 增加连接器由 Meta 提出申请，你来定。
- 增加工具服务、让命令联网，Meta 可以直接做，不用申请。
- 后续探索时，Meta 可以直接改本地的 Codex 源码。这一版先不做。
- Literature 是 Lab 的子 agent（11 月 18 日的决定），要放进 Lab Codex 里面。
- Lab Codex 自己也要能用 PDF 工具 Poppler，不只是文献工具服务。

**我替你定的，不同意请告诉我**

1. 这一版里，“Lab Codex 本身”指它的全部设置：用哪个模型和推理强度、子 agent 角色、技能、工具服务、各项开关。改源码按你说的放到后续探索（第 10 节）。
2. Meta 直接加的工具服务和联网，用两个办法让它们碰不到那四样东西：本地工具服务一律放在和 Lab 命令相同的沙箱里启动；联网走 Codex 自带的网络代理，能上外网，连不到这台 Mac 上其他程序开的本地服务。原因和测试结果见 5.3。
3. 仍然走申请的只剩三样：增加连接器或插件、读写工作区以外的文件、提高预算上限。其中“读写工作区以外的文件”你没有提到，我按原样保留。
4. Literature 分两步放进 Lab Codex：角色随第一版进去；仓库里现成的文献工具包成工具服务，作为紧接着的一个阶段（5.10）。
5. Meta 自己的职责说明和权限由你改，Meta 不能改。
6. 任务如果带检查脚本，Lab 和 Meta 都读不到它，免得答案被写进 Lab 的指示（§6“不硬编码为通用机制中的答案”）。检查脚本给出的说明只写哪里不符合要求，不写答案。
7. 每轮 Meta 最多发布一个改动（§6“每轮提出一个小幅、版本化 patch”）。
8. 一个任务就是一次 Lab 调用，适合几分钟到几十分钟的任务。
9. Lab 自己在任务中对工作区的改动（笔记、技能、子 agent）在任务结束后自动成为当前版本，同样留版本记录。
10. 控制程序自成一体，放在 RSI 文件夹里，不接仓库内核。文献工具是例外：它复用仓库里的 `rsi_literature`。
11. 任务的结果不留在 Lab 工作区，运行结束后收进记录。否则用同一个任务试跑候选版时，Lab 能看到自己上次交的结果，试跑就说明不了什么。
12. Meta 的模型和推理强度，初始也沿用 Codex 的默认值。它写在 `owner/` 里，你可以改。
13. Lab 和 Meta 的命令可以运行这台 Mac 上已经装好的命令行工具，办法是把 Homebrew 的六个工具目录放开只读。另设一个共用的 Python 环境 `env/`，Lab 可以往里装包。这两样属于初始范围，不用申请（5.2）。

## 3. 现状（2026-11-19 核对）

**RSI 文件夹。** 有 `codex-home/`（Lab 的 Codex 目录，已登录，配置里只开了 Scite、Hugging Face、GitHub、Google Drive 四个连接器和 latex、pdf 等插件）、空的 `work/`、启动脚本 `codex.sh`。没有 Meta，没有控制程序，没有记录。

**Literature 子 agent。** 两处都还没有。

- 仓库内核里，Lab 团队（PR 10）只有 Local 和 Challenge 两个子 agent 角色。Literature 仍是控制器单独调度的角色，有自己的会话，Lab 通过 `request_literature` 委托它。它有 13 个文献能力（检索、取全文、分页读原文、引用追踪、PDF 文本提取和页面渲染等），实现在 `rsi_literature` 里，由内核的控制器执行。“Literature 作为带工具服务的子 agent”是排在后面的第二个项目，11 月 18 日定了两点（不设调用上限、事后记录），还没有设计完，也没有实现。
- RSI 文件夹里没有任何子 agent 定义。现在的 Lab 是单个 Codex，可以自己用 Scite 和网页搜索查文献，但没有 Literature 这个角色。

本设计把 Literature 放进 Lab Codex：角色随初始版本进去，文献工具随后包成工具服务（5.10）。

## 4. 目标与边界

**目标**

- 一条命令跑完“任务 → 记录 → Meta 一轮”。
- 任何一次调用用的是哪个版本、花了多少、结果如何，都能从记录里查到。
- Meta 的改动不经你批准就能生效；每次发布都能追到真实的试跑，一条命令能退回。

**不做**

- 任务进行中的巡检、修复和续跑。以后要加时，这里的记录、版本、隔离和“改候选副本再发布”都用得上。
- 证明改动有收益。比较新旧版本是另外的可选步骤（P5）。
- 改 Codex 程序的源码。按你说的放到后续探索（第 10 节）。
- 让 Meta 改它自己。
- 多个 Lab 并行；一个任务分多次调用；长任务。
- 接仓库内核（`rsi_lab`）或 PABLO。

**出现任何一条即视为失败**

- Lab 或 Meta 的命令能读到检查脚本，或能改记录、任务、预算上限、控制程序。
- 引用不存在的试跑、或不是这个候选版的试跑，也能发布成功。
- 结果未知的调用被自动重发，或被记成成功或失败。
- 候选版让 Lab 用上了新的连接器，或能读写工作区以外的文件，而没有经过你。
- Meta 加的工具服务或打开的联网，让 Lab 碰到了那四样东西。
- 发布或回退之后，说不清当前是哪一版。

## 5. 设计

### 5.1 文件夹，谁能碰什么

```text
~/Desktop/RSI/
  rsi               控制程序的入口
  control/          控制程序和它的测试
  owner/            只有你改：Lab 的对外范围、预算上限、Meta 的职责说明和设置

  sealed/           封存后没能正常收尾的工作区，留给你查看
```

“Lab 的命令”一列同样适用于 Lab 的本地工具服务：它们在同一个沙箱里启动。

任务的公开部分由控制程序写进提示词，所以 Lab 不需要读 `tasks/`。Meta 通过记录看到任务的公开部分和检查结果。

这张表约束的是 agent 运行的命令，靠的是 Codex 自己的权限配置：先整个拒绝 RSI 文件夹，再逐个放开该角色需要的子目录。试跑用另一套同样写法的权限，可写的只有 `trial/`，连 `work/` 也读不到；`library/` 和 `env/` 在试跑时只读，否则一次试跑就能改掉正式的 Lab 下次要用的环境，而这中间没有任何发布。现在用的几套权限配置抄在附录里。版本库放在 `work/` 之外，所以两个 agent 都改不了版本历史。

**控制程序怎样处理 agent 能写的文件夹：先封存，再处理。** agent 能写的文件夹有六个：`work/`、`trial/`、`candidate/`、`meta/`、`library/`、`env/`。agent 启动的进程在调用结束后可能还活着，它可以在控制程序读文件的同时把文件换成指向别处的链接、把目录锁住、或者造出极深的目录。搭建时这类问题反复出现，所以定了一条规矩：控制程序不在这些文件夹里按路径读、遍历、改权限或运行 git。

- 运行前：在 `staging/` 里按要用的版本摆好一个新的工作区，然后用一次改名把它放到 `work/`（或 `trial/`、`candidate/`）的位置上。
- 运行后：先把 `work/` 整个改名成 RSI 文件夹里一个 agent 碰不到的名字，这叫封存。改名只动 RSI 文件夹里的这一个条目，agent 写不了 RSI 文件夹本身，所以抢不过来。封存以后里面不会再有新文件出现，控制程序再从这份封存的副本里收结果、跑检查、提交版本。
- 一切正常就删掉封存的副本。提交失败，或者有东西没法进版本（见 5.4），就把它移到 `sealed/` 下留着，并在记录里写明原因。
- 每次运行结束后，控制程序按最新版本重新摆好 `work/`，所以你随时可以用 `codex.sh` 手动打开 Lab Codex。

已知的缺口有两个，都写在第 10 节：封存前已经打开的文件，进程还能继续往里写；Lab 可以把 `work/` 自己锁死，这时运行会被拒绝并写明原因，要你来解开。

### 5.2 Lab 工作区里有什么

| 内容 | 位置 | 怎么生效 |
| --- | --- | --- |
| Lab 的常驻指示 | `work/AGENTS.md` | Codex 自己加载 |
| 技能 | `work/skills/<名字>/SKILL.md` | 控制程序摆放工作区时复制到 `.agents/skills/`，Codex 从那里加载。原因见下 |
| Lab Codex 的设置 | `work/codex/settings.toml` | 控制程序每次启动 Lab 前合成进 Lab 的 Codex 配置 |
| 子 agent 角色 | `work/codex/agents/<名字>.toml` | 同上 |
| 工具服务 | 在设置文件里声明；本地服务的代码放在 `work/tools/<名字>/` | 同上。本地的由控制程序改成在沙箱里启动；按网址连接的由 Codex 直接连 |
| 笔记、脚本 | 其余位置 | Lab 自己用 |

**任务的结果不在这里。** Lab 把结果写到 `out/<编号>/`。运行结束后，控制程序把这个目录收进这次运行的记录，再从工作区里拿掉。Lab 想留给自己以后用的东西，写在笔记里。

**技能为什么多绕一步。** Codex 只从工作目录的 `.agents/skills/` 加载技能，但它不让 agent 在自己能写的文件夹里新建 `.agents`，已有的也写不进去（0.170.0 上测到的）。照原来的写法，Lab 和 Meta 就永远加不了、改不了技能。所以技能放在普通的 `skills/` 文件夹里，随版本保存，Lab 和 Meta 都能改；控制程序每次摆放工作区时把它复制成 `.agents/skills/`。`.agents/` 不进版本库。Lab 在任务中改了技能，要到下一次运行才生效。只复制普通文件，链接和特殊文件跳过；上限是 64 个技能、200 个文件、合计 20 MiB，超出的不复制，并写进那次运行的记录。

**为什么设置要由控制程序合成。** Codex 只在工作目录“受信任”时才读目录里的配置文件，而一旦读，它能覆盖全部设置，包括沙箱和连接器。所以 Lab 工作区不标为受信任，工作区里也不允许出现 `.codex` 文件夹。控制程序把两部分合成一份配置：你在 `owner/` 里写的对外范围（沙箱、连接器、插件），加上 `settings.toml` 里属于“自由改”的键。Codex 本身没有“这些键锁住、那些键可改”的做法，所以这一段要自己写。

**初始版本。** `rsi init` 建立第一个版本：`AGENTS.md`、`literature` 角色文件和一份空的设置文件，模型和推理强度沿用 Codex 的默认值。它相当于 §6 的 H0，一直保留，P5 拿它和最新版本比较。`rsi init` 同时把现有 `codex-home/config.toml` 里的对外范围（权限、四个连接器、插件）搬进 `owner/`。此后这份配置文件由控制程序生成，不再手改；连接器的编号只留在本机。你原来那份配置先存成 `config.toml.before-rsi`，核对过内容一致以后才会被替换。

**手动使用。** 两次运行之间，你可以照常用 `codex.sh` 手动打开 Lab Codex，它用的就是当前版本。你留下的改动会在下一次运行前提交成一个版本，作者记为“人工或遗留”：控制程序分不清这些改动是你手动做的，还是上一次运行留下的进程做的。运行进行中不要同时手动使用。控制程序同一时间只运行一个。

**PDF 和本机工具。** Lab Codex 自己读 PDF 靠三样：已启用的 pdf 插件技能，终端里的 Poppler 命令，以及把页面渲染成图片后用看图工具看。Poppler 装在 Homebrew 下，所以 Lab 和 Meta 的权限里都把 Homebrew 的六个工具目录放开只读，其他已装的命令行工具也因此能用。文献工具服务用的是同一套 Poppler。

pdf 技能点名的三个 Python 包这台 Mac 上没有装。`rsi init` 用 Homebrew 的 Python 建一个共用环境 `env/`，Lab 的命令默认用它。按你的决定，搭建时就把这三个包（`reportlab`、`pdfplumber`、`pypdf`）从 PyPI 装进去，让 pdf 技能一开始就能完整使用；装了哪些版本记在 `owner/` 里。之后 Lab 还需要别的包时，在做任务时自己打开联网装进去，任务运行和试跑都用得上。试跑时 `env/` 只读，装不了包。`env/` 和 `library/` 一样不进版本库。

**子 agent。** 初始版本只声明 `literature` 一个角色，详见 5.10。角色文件在工作区里，所以 Lab 和 Meta 都可以改它，也可以增删别的角色。PABLO 的 Local 和 Challenge 是那个优化任务专用的，不带过来。

### 5.3 三类改动

| 类别 | 内容 | 谁定 |
| --- | --- | --- |
| 自由改 | 工作区里的所有文件。设置里的：模型、推理强度、子 agent 的数量上限和角色、技能开关、网页搜索方式；增加或去掉工具服务（本地的和按网址连接的）；打开或关闭命令联网。在你已允许的连接器和插件里关掉某一个 | Lab 工作时自己写；Meta 改候选版并自己发布 |
| 要申请 | 增加连接器或插件；读写工作区以外的文件；提高预算上限 | Meta 写申请，你决定 |
| 不能改 | 任务的冻结要求、完成判据和检查脚本；已有记录；控制程序；预算上限；Meta 自己的职责说明和权限 | 只有你 |

设置文件或角色文件里出现“自由改”以外的键时：Meta 的候选版被控制程序退回，并说明是哪个键；Lab 自己写出的不生效，并记在那次运行的记录里。

**工具服务怎样不碰到那四样东西。** Codex 默认把本地工具服务当作普通程序启动，不受沙箱约束，它能改记录，也能读到登录信息。所以控制程序生成配置时，把每个本地工具服务都改成经 `codex sandbox` 启动，文件权限和 Lab 的命令完全相同：做任务时能写 `work/`、`library/`、`env/`，试跑时只能写 `trial/`。这样 Meta 加什么工具服务都不用你批，也碰不到记录、任务、预算和控制程序。

负责启动的这一层本身在沙箱外面运行，所以它不能经过任何 agent 能写的地方：它用的是 Codex 的原生程序（绝对路径，不经过 npm 的启动脚本，那个脚本会去 `PATH` 里找 `node`，而 `env/bin` 是 Lab 能写的），`PATH` 只有系统目录，用一个单独的、空的 Codex 目录，权限配置直接写在命令行上。Lab 自己的 `PATH` 到了沙箱里面才设置。第一版没有这样做，搭建时测出 Lab 可以在 `env/bin` 里放一个假的 `node`，让它在沙箱外运行。

子 agent 的角色文件也一样：控制程序把检查过的角色文件复制到 Lab 的 Codex 目录里，让 Codex 读那份副本，不直接读工作区里的那份。

按网址连接的工具服务没有本地程序，由 Codex 在沙箱外直接连。所以只接受 `https` 加域名的网址，并且这个域名解析出来的地址必须是公网地址，免得它指向这台 Mac 或内网的服务。工具服务需要的密钥只在设置里写环境变量的名字，值由你放在启动控制程序的环境里；哪个密钥可以发给哪个域名，由你写在 `owner/` 里，Meta 加不了密钥，也不能把密钥指给别的域名。这里有一个没堵上的缺口，见第 10 节。

**联网怎样不碰到那四样东西。** 今天测到，只打开“联网”时命令是直连的：除了外网，它还能连到这台 Mac 上其他程序开的本地服务，连放在被拒绝文件夹里的 Unix 套接字也连得上。一台电脑上常见的这类服务有 ssh-agent、Docker、本地数据库，通过它们可以做到沙箱不允许的事。这台 Mac 上具体有哪些，我没有去查。所以“联网”在这里固定为两样一起开：联网，加上 Codex 自带的网络代理、所有域名放行。测试结果是外网可达，本机的 TCP 端口和 Unix 套接字都连不上。联网时 Lab 的命令可以下载并运行任何东西，但仍然只能写它自己的工作区。

联网和工具服务都记在版本里，每次运行的记录写明当时是开是关、有哪些工具服务。

申请是一条记录，写明要什么、为什么、依据哪些运行。`rsi status` 会列出待处理的申请。你同意时改 `owner/` 里的文件，Meta 不等申请结果，继续做它能做的。

### 5.4 一次任务运行

任务是 `tasks/<编号>/task.md`，四段：目标、输入、要求、完成判据。后两段是冻结的。输入如果带文件，放在 `tasks/<编号>/input/`，控制程序在启动前把它们复制到工作区的 `in/<编号>/`。可以再放一个检查脚本 `check.py`：控制程序在运行结束后执行它，把收进记录的结果目录的路径传给它；它用退出码表示是否通过，并打印一行说明。这行说明会进记录，Meta 读得到，所以只写哪里不符合要求（比如“缺少 answer.json”），不写期望的答案。检查脚本只能是你放在 `tasks/` 里的，控制程序不执行别处的脚本。

1. 控制程序核对四段齐全。缺了就拒绝启动，不猜。
2. 核对预算没有用完，核对 `rsi check` 的结果还有效（5.9），核对版本库能写。有一条不满足就拒绝启动并记下原因，不花调用。
3. 把 `work/` 里现有的东西封存。和当前版本不一样的话，先提交成一个标为“人工或遗留”的版本。然后记下当前版本。
4. 在 `staging/` 里按当前版本摆好新的工作区：检出版本，建好临时目录、`in/<编号>/`（任务的输入文件）、`out/`，复制技能。检出的内容里如果有 `.codex`，拒绝启动。然后一次改名放到 `work/`。
5. 启动 Lab：一次 `codex exec`，工作目录是 `work/`，提示词是任务的四段，加上“结果写到 `out/<编号>/`”。Lab 在这一次调用里自己完成任务，可以用命令、搜索、连接器和子 agent。
6. 结束后先封存 `work/`。从封存的那份里把 `out/<编号>/` 收进记录，对收进来的这份运行检查脚本，保存记录，再把其余的变化提交成新版本（作者记为 Lab）。最后按最新版本重新摆好 `work/`。

状态有四种：完成、出错、超时、中断。超时是到了你设的时长被控制程序停掉，算有效的观察。中断是控制程序自己被打断，结果未知：不重发，用量记为未知。调用结束以后的收尾步骤如果出了问题（比如提交失败），只在这次调用的记录里加一行问题说明，不改变它的状态和用量。

**收结果和提交版本时的几条限制**，都是为了不让 Lab 留下的东西拖垮或误导控制程序：

- 结果目录只收普通文件和文件夹，链接和特殊文件丢掉并记一行；合计最多 1 GiB、5000 个条目，超出的不收。
- 单个文件超过 256 MiB、目录嵌套过深、或者读不出来的，不进版本。出现这种情况时，封存的那份工作区留在 `sealed/` 下，不删除。
- 工作区里嵌套的 git 仓库，它的 `.git` 改名为 `.git.rsi-kept` 后当作普通文件夹保存，这样 Lab 自己克隆的代码也能进版本。
- 封存后的工作区里出现 `.codex`，不提交它，记一行。

### 5.5 Meta 的一轮

**Meta 的 Codex。** 有自己的目录和登录。连接器和插件全部关闭，网页搜索打开，命令不联网。模型和推理强度初始沿用 Codex 的默认值。它的职责说明和设置写在 `owner/` 里，控制程序把职责说明放在每轮第一次调用的提示词开头。Meta 的 Codex 设成不加载工作目录里的说明文件：`meta/` 是 Meta 自己能写的，如果照常加载，它在那里放一个 `AGENTS.md` 就等于改了自己的职责说明。Meta 也没法在 `meta/` 里给自己加技能，因为 Codex 不让它建 `.agents`。职责说明的要点取自 §6 和附件的三份 Meta 模板：先核对记录再下判断；引用记录编号；单次现象不当作规律；依据不足就不改；一次只做一个小改动；不把某个任务的答案写进 Lab 的指示；写明可能的退化；不声称收益；要扩大 Lab 的外部范围就写申请。

**什么时候开始。** 每次任务运行结束后自动开始一轮，也可以单独运行。单独运行时如果没有新的任务运行，不开始，也不花调用。只有已经结束、记录齐全的运行才交给 Meta 诊断；中断的运行只告诉它状态。

**怎么进行。** 开始时控制程序按当前版本摆好 `candidate/`（原来有的先封存）。Meta 的工作目录是 `meta/`，它在 `candidate/` 里改，自己读 `records/`。候选副本放在 RSI 文件夹下而不是 `meta/` 里面，是因为封存要靠改名，而 `meta/` 是 Meta 能写的，放在里面就抢得过来。

Meta 要求试跑候选版，或者决定发布时，控制程序先封存 `candidate/`，在封存的那份上检查（有没有 `.codex`、设置和角色文件里有没有不允许的键、工具服务合不合规、技能有没有会被跳过的），通过后存成一个快照，再按这个快照重新摆好 `candidate/`，让 Meta 接着改。试跑跑的是快照。检查没通过就没有快照，原因交回 Meta。

每次调用结束时，Meta 交回一个固定格式的决定，三选一：

| 决定 | 含义 | 控制程序接着做什么 |
| --- | --- | --- |
| 不改 | 没有值得改的，或依据不足 | 记录，本轮结束 |
| 试跑 | 列出若干项。每项是一个已有任务，或 Meta 自己写的一段小测试；并说明用候选版还是当前版 | 在 `trial/` 里逐项运行（不动 `work/`），存成记录，把记录编号交回 Meta，同一会话继续 |
| 发布 | 发布候选版，并列出作为依据的试跑记录编号 | 按 5.6 核对，通过就切换版本，本轮结束 |

Meta 自己写的小测试只是一段任务文字，不带检查脚本，结果由 Meta 自己看。用已有任务试跑时，照常运行那个任务的检查脚本。

每个决定都带同一组栏目，取自附件的诊断模板：观察到什么（引用记录编号）、问题、可能原因、其他解释、打算怎么改、预期改变什么、可能的退化、拿不准的地方。决定里还可以附申请。

一轮在 Meta 给出“不改”或“发布”时结束，或者在到达本轮的调用次数、试跑次数上限时结束。没有发布的候选版也留档。

Meta 跨轮的连续性靠两样：`records/` 里以前各轮的决定和发布记录，以及它自己在 `meta/notes/` 里写的笔记。每轮是一个新的 Codex 会话。

### 5.6 发布前控制程序核对什么

1. 本轮还没有发布过。
2. 候选版是从当前版本改出来的，并且确实有改动。
3. 候选版里没有 `.codex` 文件夹；设置文件和角色文件里只有“自由改”范围内的键。
4. 引用的每条记录都存在、已经结束（状态不是“中断”），并且跑的内容和现在的候选版完全一致。改完之后没有重跑的不算。至少引用一条。“完全一致”的判断办法：发布时给候选版存一个快照，拿快照的内容指纹和每条记录里记下的指纹比，不按路径比。

有一条不满足就不发布，原因交回 Meta。全部满足时，候选版成为当前版本，并写一条发布记录：

- 改了什么（差异）和 Meta 的诊断；
- 引用的记录；
- 本轮的全部试跑，不管 Meta 有没有引用；
- 每条试跑用的任务，是 Meta 动手之前就见过的、新的，还是它自己写的；
- 收益：未评估。

这一步证明的是“试跑是真的，跑的是这一版”，不证明“试跑结果好”。结果好不好由 Meta 判断，这是你定的。把全部试跑附上，是为了让只挑好结果引用的情况事后看得出来。

**回退。** 你可以用一条命令退到任何旧版本，记为人工。Meta 也可以把旧版本作为候选版发布，依据是那个旧版本已有的运行记录。

### 5.7 记录

- **每次 Codex 调用一份**：谁（Lab 或 Meta）、用途（任务、试跑、比较、Meta）、哪个任务、运行前后的版本、命令行、Codex 版本、起止时间、状态、用量、检查结果；提示词、完整事件流、最终答复、工作区的差异；子 agent 的过程。
- **每轮 Meta 一份**：由哪次运行触发、每个决定的原文、结果。
- **每次发布、每次回退、每个申请各一份。**

- **拒绝和封存各记一条**：哪次运行被拒绝启动、为什么；哪份封存的工作区被留下、在哪里、为什么。

每次调用开始时还记下 Codex 进程的编号和启动时间，`rsi recover` 靠它判断那个进程是不是还在。

记录只增不改，每个文件记下 sha256。只有控制程序写 `records/`。子 agent 的过程从 Lab 的 Codex 目录里按线程编号精确取出，不打开、不列出别的会话，因为那里还有你手动使用时的对话。

### 5.8 预算与记账

- 上限写在 `owner/limits.toml`，只有你改：单次 Lab 运行的时长；Meta 每轮的调用次数、试跑次数和单次时长；每天的调用总数和 token 总量。初始值我建议：Lab 单次 30 分钟；Meta 每轮最多 8 次调用、4 次试跑，单次 15 分钟；每天最多 60 次调用；token 总量先不设。
- 记账用 Codex 事件流里的实际用量，事后记。到了上限，控制程序拒绝启动下一次调用，并记下这次拒绝。一次调用中途没法按 token 截断，所以对单次调用起作用的是时长。
- 每次调用标一个成本类别（§9）：在线（任务运行）、Meta（Meta 自己的调用和它要求的全部试跑，包括没有发布的候选版）、评估（P5 的比较运行）。

### 5.9 命令

| 命令 | 作用 |
| --- | --- |
| `rsi init` | 建目录和版本库，生成两份 Codex 配置，检查两个 Codex 目录是否已登录 |
| `rsi check` | 逐项测 5.1 的表，不调用模型：命令这一层用 `codex sandbox`，包括联网打开后连不上本机的本地服务；Codex 自己的改文件工具这一层用假模型端点驱动真实的 Codex。现在约两百项，其中一部分是让 Codex 真的去执行一条终端命令（agent 的命令实际走的就是这条路）。它不在真实的 `work/` 等文件夹上测，而是在 `staging/` 下临时建一套同样结构的文件夹，配上你真实的对外范围来测。下面三样有任何一样变了，就必须重新通过才允许启动 agent：Codex 的版本、`owner/` 里的文件、控制程序自己的代码 |
| `rsi task <编号>` | 5.4 的任务运行，然后 5.5 的一轮 Meta。加 `--no-meta` 只跑任务 |
| `rsi meta` | 单独跑一轮 Meta。没有新的任务运行时不开始 |
| `rsi status` | 当前版本、最近的运行和发布、待你处理的申请、各类成本合计 |
| `rsi rollback <版本>` | 退回到某个版本 |
| `rsi recover` | 控制程序被打断后收拾现场：把没有结束的调用标成“中断”（Codex 进程还在的话先停掉它），把留在 RSI 文件夹里的封存副本移到 `sealed/` 并记一条，`work/` 不在的话按当前版本重新摆好。有没结束的调用或没收拾的封存副本时，`rsi task`、`rsi meta`、`rsi rollback` 拒绝启动，提示先运行它 |

控制程序收到 Ctrl-C、终端窗口被关掉、或者被系统要求结束时，都会先停掉正在运行的 Codex，把这次调用记成“中断”。只有被强行杀掉（来不及做任何事）时才会留下没结束的调用，这时用 `rsi recover`。

**控制程序自己用什么程序。** 它用到三个外部程序：Python、git、Codex。三个都按固定的绝对路径找，不看 `PATH`。原因是 `env/bin` 是 Lab 能写的，如果你在终端里激活了这个环境再运行 `rsi`，按 `PATH` 找就会找到 Lab 放在那里的程序，而控制程序不在沙箱里。Python 和 Codex 的位置可以用环境变量 `RSI_PYTHON`、`RSI_CODEX` 指定，指定的路径不能在 RSI 文件夹里面。

**Codex 目录里存的命令规则不生效。** 你手动用 Codex 时如果对某条命令选过“以后不再问”，Codex 会在它的目录里存一条规则，以后这条命令可以不经沙箱运行。控制程序启动 Lab 和 Meta 时让 Codex 忽略这些规则。在 0.170.0 上实测：不加这个选项时规则确实会被加载（一条“禁止”规则拦住了命令），但一条“允许”规则并没有让命令跑出沙箱。所以这一条现在是预防，免得以后的版本行为变了。`rsi check` 里有对应的测试项。你手动打开 Lab Codex 时这些规则照常有效。

**RSI 文件夹本身不能放 `AGENTS.md`、`.agents`、`.codex`。** RSI 文件夹现在是一个 git 仓库，Codex 可能把它当作 `work/` 所属的项目，从而加载放在这里的说明文件和技能。有这些文件时 `rsi init` 和 `rsi check` 会拒绝并说明原因。

### 5.10 把 Literature 放进 Lab Codex

Literature 由两部分组成，都放在 Lab 工作区里，所以 Lab 和 Meta 都能改。

**角色（随第一版）。** `work/codex/agents/literature.toml`。职责取自仓库的 Literature 设计第 1 节：在负责人交代的问题和范围内，自己拆题、选来源、检索、读全文、追引用、比较，交回回答、逐条判断和每条判断的原文出处、覆盖到什么程度、还有什么没解决。负责人决定要不要派它、怎么用它交回的东西。第一版里它用负责人会话里的 Scite、Hugging Face 和网页搜索。

**工具服务（阶段 L，紧接在 P2 之后）。** 把仓库 `rsi_literature` 的文献能力包成一个本地工具服务，名字叫 `literature`，代码放在 `work/tools/literature/`。

| 方面 | 做法 |
| --- | --- |
| 带过来的能力 | 检索论文、取论文信息、取全文、分页读原文、在已取得的文档里找段落、查引用和被引、提取 PDF 文本、渲染 PDF 单页 |
| 来源 | 先带已经真实验收过、默认启用的：Europe PMC、PubMed/PMC、OpenAlex、Asta、Poppler。Scite 不用带，Codex 里已经有它的连接器 |
| 原件 | 存在 `library/`，按内容哈希命名，不进版本库。任务运行和试跑共用 |
| 记录 | 工具服务每次调用记一行日志：输入、访问了哪个来源、取到的原件哈希。运行结束后控制程序把这次运行的日志收进记录 |
| 上限 | 不设调用上限，事后记录（你 11 月 18 日的决定） |
| 运行环境 | 和其他本地工具服务一样在沙箱里；需要联网，走网络代理 |

**沿用的规矩。** 写进角色说明：取到全文不等于读过；引用必须来自“读原文”实际交回的片段；检索命中、被引用，都不等于支持某个说法。

**和仓库里的版本差在哪。** 仓库里这些规矩由内核的控制器逐条校验：每条判断引用的证据是否真的交付过，每次调用先预约预算，中断后能对账恢复。这里没有这一层，靠的是角色说明加调用日志。Meta 抽查时可以拿日志和 `library/` 里的原件对照。

**不带过来的。** Paper2Skill（要单独的环境）；六个可选来源；图像交付的逐字节核对；需要另装 Python 包的部分。`pypdf` 这台 Mac 上没有装，先用不装包就能用的范围（各来源的检索和取全文是标准库写的，PDF 用 Poppler）。需要装包时先问你。

## 10. 已知局限与以后

- **Meta 一个人说了算，可能发布坏的改动。** 兜底是三样：每次发布都能一条命令退回；本轮全部试跑都附在发布记录上；发布记录不声称收益。
- **发布核对的门槛很低。** 一条真实的、跑完的试跑就够。它拦的是“没跑就说跑了”和“改完没重跑”，拦不住“跑了但结果其实不好”。
- **试跑复用见过的任务时，依据偏弱。** §6 要求用新的验证池。这里任务少，做不到，所以改为在发布记录里标明每条试跑的任务是不是见过的。结果虽然不留在工作区，Lab 仍可能把从那个任务学到的东西写进笔记，这本来就是它的记忆。
- **一个任务一次调用。** 长任务、需要中途接着跑的任务不在这一版里。
- **Codex 会自己升级。** 每次调用记下版本；版本变了，要 `rsi check` 重新通过才继续。行为上的其他变化只能靠记录事后发现。
- **Lab 能改自己的指示和设置。** 它在任务里写坏了自己，下一个任务就会受影响。每次都有版本，Meta 或你可以退回。
- **网络代理是实验性功能。** Codex 0.170.0 把它标为实验性。升级后它的行为变了，`rsi check` 会测出来，那时联网先关掉。
- **联网以后 Lab 的命令可以下载并运行任何东西。** 它仍然只能写自己的工作区和 `library/`，但工作区里的内容可以被发到外网。工作区里不放密钥。
- **文献工具少了内核那一层校验。** 见 5.10。
- **共用的 Python 环境不分版本。** 候选版和当前版用的是同一个 `env/`。Lab 装了什么包，只能从运行记录里查，退回版本时不会跟着退回。试跑时 `env/` 和 `library/` 只读，所以候选版如果需要新的包或新的文献原件，试跑里装不了、存不了，要等正式的任务运行。
- **Lab 可以把自己的工作区锁死。** 比如给 `work/` 加上“不可改”的标记。封存靠改名，这时改名会失败，运行被拒绝并写明原因，要你手动解开。它伤不到别的东西，只是让后面的运行停下来。
- **封存前已经打开的文件还能被写。** Lab 留下的进程如果在封存前打开了某个文件，封存后仍然可以往里写。它造不出新文件，也改不了目录结构。
- **按网址连接的工具服务，域名可以事后改指向。** 控制程序在启动前核对域名解析到公网地址，但 Codex 真正连接时会重新解析。域名的主人可以在这之间把它指到这台 Mac 上的本地服务。要彻底堵上，只能由你列一份允许的域名清单，而这和“Meta 可以直接加工具服务”相抵。现在没有这份清单，等你定。
- **`sealed/` 不会自动清理。** 留下的封存副本要你看过以后手动删。
- **技能有问题的候选版不能试跑。** 候选版的 `skills/` 里只要有一项会被跳过（一个没有 `SKILL.md` 的文件夹、一个链接、或者超出上限的部分），控制程序就不给它存快照，原因交回 Meta，Meta 要先清掉。这样试跑跑的技能和快照里的一致。`skills/` 下直接放的普通文件（比如说明文件）不算问题，只是不会被当成技能。
- **审查到最后知道、但没有修的小问题。** 都不会让 agent 碰到那四样东西，出问题时的方向都是“拒绝运行”或“少记一点”。
  - 用 `nohup` 运行 `rsi` 时，关掉终端仍然会打断它。
  - 终端的语言设置不是 UTF-8 时，`rsi` 输出中文会报错退出。
  - 编辑器在 `control/rsi/` 里留下的临时文件会让上一次 `rsi check` 的结果失效，重新运行一次即可。
  - Codex 刚好结束的那一瞬间收到中断信号，这次调用会被记成“中断”而不是“完成”，结果不会重发。
  - RSI 文件夹里只要留有没收拾的封存副本，运行就被拒绝；`rsi recover` 挪不动它的话，要你手动挪走。
  - 生成的 Codex 配置如果事后被手改，下次生成时直接覆盖，不另存。
- **以后可做。** 任务进行中的修复（做法 B）；新旧版本的比较做成命令；让 Meta 提议新的小任务进入任务库；Lab 的 Local、Challenge 等其他角色；把控制程序的做法带回仓库内核。

**后续探索：Meta 直接改本地的 Codex 源码。** 这是你定的方向，这一版不做，但现在就留两个口子：控制程序启动 Lab 用的 Codex 程序路径做成可以换的；每次调用都记下 Codex 的版本。到时候要先想清楚一件事：Lab 的沙箱是 Codex 程序自己执行的。Meta 能改这个程序以后，本文靠它守住的那四样东西就不再有保证，需要由控制程序在外面再套一层沙箱，把整个 Lab Codex 关进去。Codex 有一个给“外部已有沙箱”的情况用的启动选项，可以从这里入手。另外还需要本地的源码、编译环境和一次编译的时间。

## 11. 搭建时改了什么（2026-11-20）

| Codex 连不上模型时不会自己退出 | 0.170.0 会一直重连。所以连不上时这次调用要到时长上限才结束，状态是超时 |

**搭建中测到、以前不知道的 Codex 行为**（0.170.0）

- 命令行上的 `codex` 是 npm 的启动脚本，它靠 `PATH` 找 `node`；Homebrew 里另有一个旧版本（0.152.0）。控制程序只用原生程序的绝对路径。
- agent 在自己可写的文件夹里建不了 `.codex`、`.agents` 和 `.git`，Codex 自己拦住了；换大小写，或者换成这台 Mac 的文件系统当作同一个名字的特殊字母（比如把 s 换成长 s），也一样被拦住。新建、建链接、改名三种办法都试过。
- 这台 Mac 的文件系统把大小写不同、以及个别特殊字母写成的名字当作同一个文件。所以控制程序判断“有没有 `.agents`、`.codex`”时是去问文件系统，不是比较名字的写法。审查时发现过按写法比较会漏掉，漏掉以后复制技能那一步可以被引到工作区外面去写文件；已经改掉。
- `":minimal"` 下 `/private/tmp` 可写；每个用户自己的那个临时目录本来就读不到。
- zsh 的 here-document 用 `TMPPREFIX` 指的位置放临时文件，不看 `TMPDIR`。
- 低推理强度下，模型不会去尝试写工作区以外的文件，所以这类情况一律用假模型端点来测。

## 附录：权限配置和测过的写法

`<RSI>` 代表 `~/Desktop/RSI` 的完整路径，`<HOME>` 代表个人目录。实际文件里写完整路径。下面是控制程序现在生成的写法（2026-11-20）。Lab 的 Codex 配置里有四套：`lab`、`trial`，以及联网打开时用的 `lab_net`、`trial_net`。Meta 的配置里有一套。

```toml
# Lab 做任务时用。
default_permissions = "lab"

[permissions.lab.filesystem]
":minimal" = "read"
"<RSI>" = "deny"
"<RSI>/work" = "write"
"<RSI>/library" = "write"
"<RSI>/env" = "write"
"<RSI>/codex-home/plugins/cache" = "read"
"/opt/homebrew/bin" = "read"
"/opt/homebrew/Cellar" = "read"
"/opt/homebrew/opt" = "read"
"/opt/homebrew/lib" = "read"
"/opt/homebrew/share" = "read"
"/opt/homebrew/etc/fonts" = "read"
"/private/tmp" = "deny"
"/private/var/tmp" = "deny"
"<HOME>/.codex" = "deny"
"<HOME>/.codex-rsi-lab" = "deny"

[permissions.lab.network]
enabled = false

# 试跑时用，启动时用一个参数选它：-c 'default_permissions="trial"'
# 和 lab 只差三行：可写的是 trial/，library/ 和 env/ 只读。
[permissions.trial.filesystem]
"<RSI>/trial" = "write"
"<RSI>/library" = "read"
"<RSI>/env" = "read"
# 其余各行同上，没有 "<RSI>/work" 那一行

[permissions.trial.network]
enabled = false
```

```toml
# Meta 用。
default_permissions = "meta"
project_doc_max_bytes = 0        # 不加载工作目录里的说明文件（5.5）

[permissions.meta.filesystem]
":minimal" = "read"
"<RSI>" = "deny"
"<RSI>/records" = "read"
"<RSI>/work" = "read"
"<RSI>/library" = "read"
"<RSI>/env" = "read"
"<RSI>/meta" = "write"
"<RSI>/candidate" = "write"
# Homebrew 的六行、临时目录的两行、个人目录的两行同上

[permissions.meta.network]
enabled = false
```

和批准时那一稿相比，改了四处：

- 去掉了 `"<RSI>/work/.codex" = "read"` 这类条目。Codex 本来就不让 agent 在可写的文件夹里新建 `.codex`；加上这一条以后，如果 `.codex` 是一个指向别处的链接，Codex 会顺着链接把那个地方变成可读，搭建时测到它把 `owner/` 变成了可读。
- 拒绝了系统的公共临时目录。`":minimal"` 下 `/private/tmp` 是可写的，Lab 和 Meta 可以经它互相传东西。命令的临时目录改在各自的工作区里，zsh 的临时文件也指到那里（`TMPPREFIX`）。
- 试跑时 `library/` 和 `env/` 只读（5.1）。
- Meta 多了 `candidate/` 可写（5.5）。

测的方法是 `CODEX_HOME=<那个 Codex 目录> codex sandbox -- <命令>`，不调用模型。测到的要点：

- 先拒绝整个文件夹、再放开子目录是有效的，写得更具体的那一条优先。
- `":minimal"` 不会让个人目录里的其他文件变得可读。
- 插件缓存要单独放开只读，否则 Lab 的命令读不到插件带的技能文件。
- 命令需要一个可写的临时目录。把 `TMPDIR` 指到工作区里的一个子目录后，系统自带的 `python3` 才不报错。
- 这些只说明 agent 运行的命令受约束。Codex 自己的工具要用真实调用核对（第 3 节）。

**本机工具和共用环境。** 上面 Homebrew 的六行在 Lab 和 Meta 两套上测过：Poppler 的三个命令能用，共用环境里的 `python3` 和 `pip` 能用，Homebrew 的 `var/` 和其余 `etc/` 仍然读不到，这些目录都写不了。

命令的 `PATH` 要把 `<RSI>/env/bin` 和 `/opt/homebrew/bin` 放在前面。

**联网打开时**，改用 `lab_net`（试跑用 `trial_net`）。文件部分和上面相同，网络部分是下面的写法，并打开 `network_proxy` 这个功能开关（测试时用的是 `--enable network_proxy`）：

```toml
[permissions.lab_net.network]
enabled = true
mode = "full"

[permissions.lab_net.network.domains]
"*" = "allow"
```

今天的对照测试，都在沙箱里的命令中进行，外面开了一个本机 TCP 监听和三个 Unix 套接字：

| | 联网关 | 只开联网 | 联网加网络代理 |
| --- | --- | --- | --- |
| 访问外网（https） | 不通 | 通 | 通，经过代理 |
| 连本机的 TCP 端口 | 不通 | 通 | 不通，代理答复 `not_allowed_local` |
| 连 Unix 套接字，包括放在被拒绝文件夹里的 | 不通 | 通 | 不通 |
| 写 `records/` | 不行 | 不行 | 不行 |

**本地工具服务放进沙箱的写法**（控制程序现在生成的；批准时那一稿的写法更简单，问题见 5.3）：

```toml
[mcp_servers.<名字>]
command = "<Codex 原生程序的完整路径>"
args = ["sandbox", "-c", "permissions=<上面四套权限，写成一行>", "-P", "lab", "--",
        "/usr/bin/env", "PATH=<RSI>/env/bin:/opt/homebrew/bin:/usr/bin:/bin:/usr/sbin:/sbin",
        "TMPPREFIX=<RSI>/work/.tmp/zsh", "<服务的命令>", "<RSI>/work/tools/<名字>/server.py"]

[mcp_servers.<名字>.env]
CODEX_HOME = "<RSI>/codex-home/rsi/wrapper-home"   # 单独的、空的 Codex 目录
TMPDIR = "<RSI>/work/.tmp"
PATH = "/usr/bin:/bin:/usr/sbin:/sbin"
```

试跑时把 `lab` 换成 `trial`，路径换成 `trial/` 下的那份。服务要联网时用 `lab_net`，并加上网络代理的开关。Codex 的原生程序由环境变量 `RSI_CODEX` 指定，或者由控制程序从 npm 的安装位置里找出来；找到的如果是脚本，拒绝使用。由 Codex 启动这样的服务、由子 agent 调用，已在开工第一步用真实调用确认过（第 3 节，当时用的是第一稿的写法）；现在这个写法由 `rsi check` 不调用模型地测。

**改文件工具的八种情况**（开工第一步，Codex 0.170.0，批准方式为“从不询问”，权限是上面 Lab 那一套）。做法是让 Codex 连到一个本机的假模型端点，端点按脚本要求 Codex 调用改文件工具；不调用真实模型，也不需要登录。

| 让工具做什么 | 工具的回答 | 磁盘上 |
| --- | --- | --- |
| 在工作区里新建文件 | 成功 | 有 |
| 用绝对路径在被拒绝的文件夹里新建 | `patch rejected: writing outside of the project; rejected by user approval settings` | 没有 |
| 经工作区里的符号链接在外面新建 | 路径检查放行，写入失败：`Failed to write file` | 没有 |
| 用 `..` 路径在外面新建 | `patch rejected: writing outside of the project…` | 没有 |
| 在既没放开也没拒绝的文件夹里新建 | `patch rejected: writing outside of the project…` | 没有 |
| 新建工作区里的 `.codex/config.toml` | `patch rejected: writing outside of the project…` | 没有 |
| 改写工作区外已有的文件 | `apply_patch verification failed: Failed to read file to update … Operation not permitted` | 原样 |
| 删除工作区外已有的文件 | `apply_patch verification failed: Failed to read … Operation not permitted` | 还在 |

假模型端点的接法，供实现时照做：Codex 的配置里写 `model_provider = "mock"`，再加一段 `[model_providers.mock]`（`base_url` 指向本机端口，`wire_api = "responses"`）。端点收到 `POST /v1/responses` 后用事件流回答：一条 `response.created`，若干条 `response.output_item.done`，一条 `response.completed`。在 0.170.0 的默认模型下，模型调用工具的方式是发一个名为 `exec` 的调用，内容是一段 JavaScript，里面写 `await tools.apply_patch(...)` 这样的调用；工具的回答出现在下一次请求的输入里。
