## 1. 摘要

**要做的事。** 文献原件已保存在 `library/`，工具回执和研究结果保存在 Lab 无法读取的 `records/`。这次加一个跨任务的证据台账。控制程序从任务回执中登记证据对象，并把每次交付指向具体的对象版本。下一项任务可以查到过去返回的段落、出处和核验状态，按对应的文档编号、文档版本和定位引用。

**一圈怎么走**

1. 摆放：控制程序摆放工作区时，放进一份记忆库的快照。
2. 运行：Lab 用一个工具服务检索快照；需要时照常取新的原文。
3. 登记：运行结束后，控制程序从这次运行的会话记录里找出文献工具服务的调用，核对后追加进库。
4. 记录：运行记录保留启动时实际使用的快照信息。登记报告记下本批结果和流水末尾的校验值。登记完成后，控制程序给手动打开的 Lab 摆放新的快照。

```text
任务运行                     运行结束                              下一次运行
Lab 检索快照              ─▶ 控制程序：                        ─▶ 摆放工作区时放入快照
Lab 取原文、派 Literature    1 从会话记录找出文献工具服务的调用     （试跑：去掉同一个任务的内容）
（第二步：Lab 写提议）        2 核对，通过的追加进库                Lab 用工具服务检索
                             3 没通过的写明原因
                                     │
                                     ▼
                             memory/（只追加，带版本号）
```

**分两步交付**

| | 库里多了什么 | 靠谁 |
| --- | --- | --- |
| 第一步：证据台账 | 交回过的原文段落、取全文的成败、论文的标识 | 全部由控制程序从记录里得出，不需要 Lab 配合 |
| 第二步：Lab 的提议 | 问题、判断、决定、调查、做法经验 | Lab 在任务里提议，控制程序核对后登记 |

第一阶段的证据登记、快照和权限见 5.2 至 5.8。第二阶段沿用同一条台账，提议、引用、撤回和检索的约定见 5.9。

**你已经定的**（前两条是你直接说的；后五条是你选做法二时，随那个做法一起定下的）

- 用途是跨任务复用证据。
- 库单独存放，只有控制程序能写；分两步，第一步只做自动的证据台账。
- Lab 的提议要经控制程序核对才登记，登记时“支持情况”固定写“待核对”。
- 检索的代码放在工作区里，Meta 可以改进；库的内容、格式和登记规则 Meta 改不了。Meta 对库只读。
- 试跑拿到的快照里去掉来自同一个任务的内容，以及由它们推出的内容；试跑里的内容不登记。
- 验收时同一个后续任务带记忆和不带记忆各跑一次，只给对照表，不下“有收益”的结论。
- 参考 MolRSI 和 InfraRSI 的记忆设计。

**我替你定的，不同意请告诉我**

1. **登记表示文献工具服务在该次调用中交回了这段文本。** 库分别记录交付出处与原件复核状态。能从原件逐段复核的引文可另作标注。会话记录能证明什么，见 5.4。
2. “证据”按宽的理解：取到的原文、算出的结果、试过的做法和失败都算。第一步只登记文献工具服务给出的三样（5.3）。算出的结果等有了计算工具服务再加。
3. 段落按“原件哈希、解析器版本、定位”编号，不按文档编号。同一份原件用不同的论文标识取两次，会得到两个文档编号，但它们是同一批段落（R0009 和 R0012 就是这样）。
4. 查询时根据可见的论文标识记录和各次获取回执判断论文归属。相同原件可以共用段落；论文标识的冲突及其依据分别保留（5.6）。
5. 控制程序为了核对原件，会按哈希名只读打开 `library/objects/sha256/` 里的文件。design.md 5.1 写的是控制程序不碰 `library/`，这是一个窄的例外，理由和限制见 5.4。
6. 任务检查脚本的结果、Meta 的决定和笔记，不进记忆。
7. 出错和超时的运行照常登记。中断的运行不登记：它的记录里没有会话文件。
8. 加一个开关 `rsi task <编号> --memory none`：这次运行不给记忆，它取到的东西也不登记。验收的对照要用它。
9. 你手动打开的 Lab Codex 读得到快照，但它取的东西不登记，因为那些会话不归控制程序收集。
10. 工作区顶层的 `memory/` 这个名字归控制程序用，和 `in/`、`out/` 一样不进版本。现有的 V0001 到 V0008 都没有这个名字。
11. 每条交付记录该次调用实际使用的服务入口。能将入口对应到受版本管理的实现时，再标注代码来源；其他入口按可获得的信息标为自定义或未知（5.4）。
12. 用现有记录回填第一批内容：所有满足条件的任务运行，现在有文献调用的是 R0009、R0010、R0012、R0013。
13. 登记不调用模型，不计入调用预算。
14. 工作区里的文件用英文：工具服务、技能、Lab 指示里新增的几行。给 Meta 的几句说明由控制程序放进每轮的提示里，和现在文献回执那一句的做法相同，不用改 `owner/` 里的职责说明；措辞写在 5.8，请一并看。
15. 验收用的后续任务由我起草，你看过再跑。

## 4. 目标与边界

**目标**

- 在下一个任务里，Lab 能查到本次快照收录的历史段落，按可见交付的文档编号、版本和定位引用，并分辨段落是否经过独立的原件复核。
- 每一条证据都能追到交回它的运行、线程和调用。段落和已取得的文档还能追到对应的原件。
- 任何一次运行用的是哪一版记忆、带着什么条件，从记录里查得到。
- Lab 和 Meta 都改不了库里的内容。Meta 能改进的是 Lab 怎么用它。

**不做**

- 判断一条说法是不是真的被原文支持。这一栏只写“待核对”。
- 认定模型是不是看过某一段（5.4）。
- 向量检索，或任何外部数据库。检索是确定的词面匹配。
- 任务进行中的登记。一个任务是一次调用，登记在调用结束后做。
- 把新证据自动和旧判断配对、自动归纳、遗忘。
- 把算出的结果登记成证据。现在没有带回执的计算工具服务。
- 登记你手动会话里取到的东西；登记中断的运行。
- 把上游内核搬过来，或者和上游的库互相导入导出。对象的写法和上游对得上，以后要做时不用改库。
- 证明记忆有收益。

**出现任何一条即视为失败**

- Lab 或 Meta 的命令能改库里已有的内容。
- 会话记录里没有的内容被登记成了证据，或者登记的文本和工具服务当次交回的不一样。
- 同任务独有的修订、出处或别名能从试跑的快照或检索结果查到，或者试跑里的内容进了库。
- 仅凭相同文件就合并了相互冲突的论文标识，或把仅经哈希核对的段落标作已从原件逐段复核。
- 检查脚本的结果或 Meta 的决定，经过记忆传到了 Lab 手里。
- 同一次运行登记两遍，库里出现了重复的内容；或者登记到一半被打断，库坏了却发现不了。
- 登记这一步出问题，改变了那次调用的状态、用量或已有的记录文件。
- 给 Lab 的旧内容没有标明来自哪次运行。

## 5. 设计

### 5.1 文件夹，谁能碰什么

在 design.md 5.1 的表上加两行：

| | Lab 的命令 | Meta 的命令 | 控制程序 |
| --- | --- | --- | --- |
| `memory/`（库，在 RSI 文件夹下） | 读不到 | 只读 | 只有它写 |
| 工作区里的 `memory/`（快照） | 读写。改了只影响它自己这一次运行 | `work/` 里的那份只读，和 `work/` 其余部分一样 | 摆放时放入；不进版本；随封存的工作区一起丢弃 |

Lab 的几套权限都不用加条目：RSI 文件夹整个是拒绝的，`memory/` 没有被放开。Meta 的权限加一行 `"<RSI>/memory" = "read"`。`.gitignore` 加一行 `/memory/`，库和 `records/`、`library/` 一样只留在本机。

库不随 Lab 工作区的版本走。发布、回退都不动它。

### 5.2 库

库是普通文件，用 Python 标准库读写。具体的文件名和布局留给实现者，但要满足下面五条：

1. **只追加。** 已经写进去的对象版本和登记事件不再改动、不删除。
2. **有版本号。** 库里有一份登记事件的流水，一行一个事件，带从 1 开始的序号。整批提交后，末序号成为新的“记忆版本”。
3. **改了能发现。** 每行带上一行的哈希，每个对象版本带自己的内容哈希。库外每份登记报告都保存该批次的末序号和末行哈希。`rsi memory verify` 重算流水和对象，逐批与报告对账，包括最后一批。末行被修改或整段尾部丢失都应报错。
4. **登记可以重做。** 每次运行按运行号整批提交，再写库外登记报告。若在两步之间中断，重试按已提交的批次补写报告。若已有报告与批次不符，保留现场并报错。具体的恢复规则见 5.4。
5. **能回到过去。** 给一个已提交的记忆版本号，能重建该批次结束时的对象版本和交付。

除了流水和对象，其余的东西（按原件、按论文标识、按运行的索引）都能从这两样重建。

每个对象版本的外层字段和上游对齐：

```json
{
  "schema_version": "rsi_mol_memory_v1",
  "id": "…", "kind": "evidence", "revision": 1, "supersedes": null,
  "question_ids": [], "source_refs": [], "object_refs": [],
  "content": { "…": "见 5.3" },
  "origin": { "run": "R0010", "task": "paired-validation", "version": "V0006" },
  "authority": "receipt",
  "record_sha256": "…"
}
```

`authority` 有三个值。`receipt` 表示控制程序从会话记录里得出的，第一步的证据全是这个值。`task_contract` 表示从任务目标生成的根问题，`model_interpretation` 表示由 Lab 提议、经登记的解释对象或子问题。`question_ids`、`source_refs`、`object_refs` 在第一步是空的。库中的 `origin` 记首次登记的出处。快照中显示的出处按 5.5 从可见交付生成。

### 5.3 证据的三种记录

第一步登记三种证据，都来自文献工具服务（`literature`）的调用。

| 种类 | 来自哪个工具 | 记什么 | 编号由什么决定 |
| --- | --- | --- | --- |
| 段落 `passage` | `read_document`、`find_passages` | 工具交回的完整文本、控制程序算出的段落文本哈希、定位、原件哈希、解析器版本、字符和字节范围、所在章节、段落类型 | 原件哈希、解析器版本、定位 |
| 取全文 `acquisition` | `acquire_fulltext` | 当次请求的论文标识或本地来源编号、来源、结果。取到时保留文档编号和版本、原件哈希、媒体类型、内容范围、服务报告核对过的标识种类及镜像结果。来源端未取到时保留错误码、所处阶段和回执中的访问记录 | 运行编号加这次调用的编号。每次符合登记条件的尝试各记一条 |
| 论文标识 `paper` | `get_paper`、`search_papers`、`get_citations` | 交回的每篇论文：来源里的编号、DOI、PMID、PMCID、标题、年份。不存摘要 | 来源里的编号（带来源名，比如 `europe_pmc:MED:19505943`） |

**交付。** 每次工具调用交回一条证据，就在流水里将这次调用绑定到具体的 `(id, revision)`，记录运行、任务、发起调用的线程及角色、调用编号、时间和服务来源标注（5.4）。同一段落再次交回，会给同一修订增加一条交付。来源后来修正 DOI 时，旧交付仍指向当时的论文标识修订。

段落的交付还记当时的文档编号、文档版本、内容范围（如全文、摘要或节选），以及回执里的论文标识、来源和网址。由 PDF 提取的文本另记上一级文档和原 PDF 的哈希。这样即使两次交付的文本相同，也能区分各自的归属和适用范围。

**五点说明**

- **同一份原件的同一段只有一个对象。** 不同文档编号作为别名保留在各自的交付上。原件哈希只用于识别文件和去重段落。论文归属按原始请求、来源标识及回执里的核对情况分别查询（5.6）。
- **段落只收完整的。** `block_complete` 为假的段落是被分页切开的，不登记，在报告里记一个数。R0009 有 3 个。
- **没取到时按失败阶段登记。** 错误码及回执细节能定位到来源端时，登记当次事实，例如所选格式没有下载候选，或镜像返回 HTTP 404。参数错误、本地依赖缺失（`runtime_unavailable`）、本地归档失败（`source_storage_error`）、输出过大只写入报告并区分原因。HTTP 200 后写盘失败归为本地归档失败。旧回执或自定义服务给不出足够信息时，在报告记“原因不明”。单凭 `unavailable`、`failed`、访问过主机或出现下载尝试，都不足以判断来源端失败。
- **论文标识可以有新版本。** 同一个来源编号后来交回了不同的 DOI 或标题，追加成这个对象的新版本，旧的留着。
- **别的工具不登记。** 渲染 PDF 页面、整理阅读索引、Asta 的工具，第一步都不登记。页面图片现在没有一次真实运行的例子可以对照。

### 5.4 运行结束后的登记

**什么时候做。** 登记是单独的一步，在一次任务运行的调用记录定稿之后做，还在同一条 `rsi task` 命令里。它只对满足下面全部条件的运行做：

- 用途是任务，不是试跑；
- 记忆条件不是 `none`（5.5）。没有这一栏的旧记录按正常条件算；
- 状态是完成、出错或超时，不是中断；
- 记录里有会话文件。

每次任务运行开始前，控制程序先按运行顺序补齐符合条件的登记及其报告，再做快照。任务结束后的手动工作区按 5.5 的顺序刷新。

**用什么做依据。** 读取已定稿调用记录中的运行信息、实际启动配置，以及负责人线程和各级子 agent 的会话文件。原件哈希在 `library/` 核对；服务来源通过实际配置和运行所用的工作区版本核对。登记无需读取当前工作区或 `literature.jsonl`。旧记录缺少的配置或回执字段按未知处理。

**找哪些调用。** 在会话文件里找“工具调用完成”的事件，取服务名是 `literature`、工具属于 5.3 那六个的。正常交回的都看；`acquire_fulltext` 另外也看标成错误的（5.3 的第三点）。子线程继承的调用归回实际发起的线程。一次运行内，同一个 `invocation_id` 的同一调用只算一次；同号但工具、参数或返回内容冲突的记入报告，留待核对。

**逐条怎么核对**

| 核对 | 没通过时 |
| --- | --- |
| 交回的内容能按 JSON 解析，大小在上限以内，需要的字段齐全、类型对 | 这一条不登记 |
| 段落：`block_complete` 为真 | 不登记，只计数 |
| 段落和取到的全文：`library/objects/sha256/<原件哈希>` 存在，内容的 SHA-256 等于它的文件名 | 不登记，原因写“原件不在”或“原件哈希对不上” |
| 段落：库里已有同一个编号的对象时，文本必须相同 | 不登记，并在报告里单列：同一份原件、同一个解析器版本、同一个定位出现了两种文本 |
| 取全文没取到：按 5.3 的错误码和阶段能判为当次来源端结果 | 本地故障和原因不明的情况分别写入报告 |

没通过的每一条都写进报告，带原因。没通过不影响其他条目。

**登记认定的是什么。** 一个段落进了库，说明三件事：

1. 那次运行里，文献工具服务把这段文本交回给了 Lab，会话记录里有这次调用；
2. 它声称来自的原件在 `library/` 里，哈希对得上；
3. 调用记录能确认的服务入口和版本归属已随交付标注，缺失项标为未知。

它不说明两件事：

- **模型看过这段。** Lab 是在脚本里调用工具的，模型看到的是脚本打印出来的部分，太长会被截断。实测 R0010 的子线程：交回的 41 个完整段落里，有 1 个没有出现在模型看到的任何输出里。
- **原件里确实有这段话。** 核对这一点，要用控制程序自己那份解析代码重新解析原件再比对。`tasks/lit-service/audit.py` 已经能对 XML 原件这样做，但要你手动运行。

第一步用会话里的工具回执登记历史交付，便于后续任务重新找到对应材料。现有核验脚本另有独立重建 XML 原件的步骤；这项复核与登记分开记录。第二步设计再确定 Lab 提议判断时需要哪种交付依据（5.9）。

**服务来源的标注。** 从这次调用的实际启动配置提取生效的 `mcp_servers.literature`。对本地服务核对包装后的命令、参数和解析出的入口与运行开始时的版本树；只有能对应到预期入口，才附上该版本中 `tools/literature/` 最后一次改动的版本和提交者（安装、初始、Lab、Meta、人工或遗留）。配置改为另一脚本或 URL 时标“自定义入口”并记录可识别的入口信息；旧记录缺配置或无法定位入口时标“来源未知”。服务名相同不能单独证明归属。

同时记录运行前后提交中启动配置和服务代码有无差异，提交失败记“无法判断”。例如“启动配置对应 V0008 安装的入口，前后提交未见改动”。这个标注只描述可核对的配置和版本；环境依赖或运行期间改动后又还原的文件仍可能影响结果。

**读 `library/` 的限制。** design.md 5.1 规定控制程序不在 agent 能写的文件夹里按路径读东西。这里要读原件来核对哈希，所以定一个窄的例外：只按哈希名打开 `objects/sha256/` 下的一个文件，从 RSI 文件夹的描述符逐级打开，不跟链接，只接受只有一个链接的普通文件，超过大小上限就放弃，只读，读出来只用来算哈希。读不到、对不上，结果都是“不登记”。留下的进程即使在这时换掉文件，也只能让核对失败，不能让一个错的哈希通过。`tasks/lit-service/audit.py` 和 `control/rsi/literature_logs.py` 里已经有这样的读法。

**写进库。** 用运行编号标识一次提交。先将新对象修订、交付及重建报告所需的登记摘要作为同一批次提交，再写库外报告。一次提交作为整体对读者可见；有登记资格但没有可收条目的运行也保存处理结果，供后续补登识别。

**出问题时。** 登记在调用记录定稿后单独执行，设有时长上限。库内提交前中断，重试时重做该批；提交后、报告写完前中断，重试时从已提交批次补报告。每次先按运行编号确认提交状态。已有报告与库内记录不符时报告校验失败，保留现场供核查。终端报告登记错误，原调用的状态、用量和记录文件保持原值。

**报告。** 控制程序在库外写一次 `records/memory/<运行编号>.json`。报告保存运行编号、提交前后记忆版本、该批事件数、提交末行哈希、各类证据与交付条数、服务来源、未登记条目及原因。`rsi memory verify` 按运行和序号将每份报告与库内批次及其末行哈希对账；末行丢失、被改写或整批缺失均应指出。补登以库内批次和库外报告共同判定完成。

**上限。** 一次运行最多登记的条数、单个段落的大小、一次运行登记的总字节数，都设上限，数值留给实现者。超出的不登记，报告里写明数量。

### 5.5 快照和三种运行条件

Lab 读不到库，读的是控制程序在摆放工作区时放进去的一份快照，放在工作区顶层的 `memory/`。控制程序决定快照里放什么，这是规矩；Lab 的工具服务决定怎么从里面挑，这是可以改进的做法。

| 条件 | 什么时候用 | 快照里有什么 | 这次运行登记吗 |
| --- | --- | --- | --- |
| 正常 `live` | 默认任务运行；任务结束后供手动打开的 `work/` | 摆放时最新已提交的记忆 | 任务运行登记；手动会话不登记 |
| 试跑 `trial` | 所有试跑，不能选 | 库的当前内容，去掉同一个任务的内容 | 不登记 |
| 不给 `none` | `rsi memory source-changed <SHA-256>` | 按已登记的原件哈希标记来源变化，新快照显示受影响的引用 |
| `rsi memory withdraw <编号> <修订号>` | 撤回确切修订，在后续快照中沿引用传播不可用状态 |
| `rsi task <编号> --memory none` | 只有一个说明文件，写着这次运行没有记忆 | 不登记 |

**试跑如何排除同任务的证据。** 有任务编号 T 的试跑按以下顺序生成快照。

1. 去掉任务 T 的交付。按对象编号和修订号 `(id, revision)` 保留仍有可见交付的版本。同一个编号的“当前版本”取可见版本中最新的。例如 A 交回某篇论文的第一版，只有 T 交回改了 DOI 的第二版，试跑 T 时只放入第一版。
2. 对保留的版本，用最早的可见交付填写快照里的 `origin`。文档别名、论文标识关联、索引、任务数和最近交付时间都只取自可见数据，检索和排序也只使用这些数据。`supersedes` 仅在它指向的原版本可见时显示。这样，即使同一段最早由 T 交回，只要 A 也交回过它，试跑 T 仍能用 A 的出处引用。
3. 第二步的判断等对象也按版本处理。排除 T 提议的版本，随后依次排除引用了已排除证据或对象版本的提议，直到余下引用都可见。

Meta 自己写的小测试没有任务编号，按当前库版本和容量上限生成快照，记录里写明未按任务排除。一轮 Meta 期间库版本固定，候选版和当前版对同一任务试跑时得到同一份快照。

**快照的要求。** 用标准库就能读的普通文件，带一个说明文件：记忆条件、所用库版本、各类条数，以及按条件排除和因容量省略的数量。先执行可见性规则，再按最近的可见交付优先装入。库内的 `record_sha256` 用来核验完整对象版本。快照中重建了 `origin` 或筛去 `supersedes` 等字段的记录省略该哈希。每次调用开始时，对实际摆放的整份快照算指纹，连同这些数量写进运行记录。

**手动工作区何时刷新。** 任务调用记录定稿后，先处理本轮登记，再按最新已提交的记忆重新摆放供手动使用的 `work/`。即使本轮使用 `none`，手动工作区也恢复 `live`。沿用控制程序在 `staging/` 备妥工作区再整体换入的做法。若本轮在提交前登记失败，仍用上一次完整提交的记忆恢复手动工作区，并报告原因。运行记录里的快照指纹始终对应调用开始时的那一份。

**快照不进版本。** 把 `memory/` 加进不进版本的顶层名字。Lab 改了自己工作区里的快照，只影响它自己这一次运行：登记从不读快照。候选副本 `candidate/` 里不放快照，Meta 直接读库。

### 5.6 Lab 怎么读：工具服务和技能

这一节的东西都在 Lab 工作区里，随版本走，Lab 和 Meta 都能改。

**工具服务。** 名字叫 `memory`，代码在 `tools/memory/`，和文献工具服务一样用标准输入输出说话，由控制程序放进沙箱启动。检索在本地读取工作区快照，普通 live 任务还可向专用目录提交提议。种子的设置文件里加：

```toml
[tool_servers.memory]
command = "python3"
args = ["-B", "tools/memory/server.py"]
```

前四个工具用于证据台账。第二阶段增加两种检索和一个提议工具。

| 工具 | 做什么 |
| --- | --- |
| `memory_status` | 这次运行的记忆条件、记忆版本、各种内容的条数、去掉和没放进去的数量 |
| `lookup_sources` | 按 DOI、PMID、PMCID、来源编号、文档编号或标题查候选论文。列出相符的来源记录、当次获取请求及其结果、可见段落和出处，并显示论文归属的依据和冲突 |
| `recall_passages` | 用一句话或几个词检索段落。可以限定论文、原件、任务。返回排好序的段落，带文本和出处 |
| `get_evidence` | 按编号、可选修订号取快照中可见的对象版本及其可见交付；省略修订号时给出最新可见修订 |
| `recall_judgments` | 检索判断、适用条件、出处和挑战材料 |
| `recall_objects` | 跨种类检索，或指定种类。结果保留关联对象的确切修订和新鲜度 |
| `propose_memory` | 普通 live 任务提交子问题、判断、决定、调查或做法经验，成功时返回待登记编号 |

**论文怎么连起来。** 检索工具读取本轮启动时的快照。先按 5.5 选出可见修订和交付，再从中建索引。对同一来源编号，默认用最新可见修订；查询旧修订时保留其当时的标识。检索时分别列出三种依据：

1. **来源记录。** 同一修订里并列出现的 DOI、PMID、PMCID 和来源编号可以互查，比较前按标识种类规整。标题只用于找候选。
2. **获取请求。** 查询标识或某个来源修订中的标识与当次请求相符时，列出该次获取，并原样注明“请求匹配”和服务当时报告核对过的标识种类。旧回执缺字段或列表为空时标“未核实”。例如 R0009、R0012 的查询回执都把 `PMC2723002` 和 `europe_pmc:MED:19505943` 连到同一个 DOI，由此可找到各自的获取请求。
3. **文档与段落。** 通过获取记录里的文档编号、版本和原件哈希，连接具有相应别名的段落交付；PDF 提取文本经上一级文档及 PDF 哈希连接。同一文件可供多次请求复用。若不同 DOI 对应同一个 PDF，分别列出请求、标识依据和冲突，只展示各自有交付支撑的段落关联。相同字节、相似标题或一条记录里的不同历史修订，都不能作为合并两篇论文的依据。

**每个段落带什么。** 证据编号和修订、文本及其哈希、原件哈希、解析器版本、定位、章节、可见交付中的文档编号和版本（最近的在前）、相关论文标识及关联依据、来源运行、任务和服务标注。第一步的固定提示为“历史文献工具返回的文本。原件哈希已核对，段落尚未与原件逐段复核。” 段落复核状态独立于论文标识和原件哈希的核对状态。以后只有从对应原件独立重建并比对了这条修订，才可追加“已复核”的标注和核验出处。

**先筛后排，给多少由调用者定。** `recall_passages` 按调用者给的条件筛选，再按标识匹配、词面匹配程度、可见交付的任务数、最近可见交付的先后排序。排序是确定的，同样的快照和问题得到同样的结果。调用者可指定返回字节上限，有默认值；响应列出因此省略的条数。打分的细节留给实现者，Meta 以后可以改。

**技能和指示。** 加一个技能 `skills/scientific-memory/SKILL.md`，Lab 的指示和 `literature` 角色的说明各加几行。要点：

- 任务开始时先看 `memory_status`，再用任务的问题检索一次。
- 派 Literature 之前、取全文之前，先用 `lookup_sources` 查这篇论文。
- 引用记忆里的段落时，写明证据编号和修订、文档编号和版本、定位、原件哈希及逐字引文，并列出交回它的来源运行。
- 记忆里有，不等于这次读过。任务要求这次运行里实际读到原文时，按记忆里的文档编号和定位用 `read_document` 再读一遍。
- 使用前查看段落复核状态和论文标识的依据，再判断它是否支持当前说法。
- 交结果时标明段落是本轮记忆工具交回、本轮文献工具重新读取，还是两边均有交付。

### 5.7 记录、命令和检查

**记录。** 每次 Lab 调用的 `call.json` 加一栏 `memory`，记录开始时的记忆条件、记忆版本、快照指纹、按条件排除和因容量省略的数量。登记后的记忆版本及该批次末行哈希写在独立的登记报告里（5.4）。发布记录里，本轮每条试跑后面写上它的记忆条件和记忆版本。没有这一栏的旧记录照常能读。

**命令**

| 命令 | 作用 |
| --- | --- |
| `rsi install-memory` | 给已有的安装装上：把工具服务、技能、设置里的那一段、指示里的几行并进当前工作区，存成一个新版本。做法和 `rsi install-literature` 相同：先把工作区里没提交的改动存成一个版本作为回退点，有冲突就报告、不动手，装第二遍什么也不做 |
| `rsi memory status` | 记忆版本、各种内容的条数、最近几次登记、还有几次运行没登记 |
| `rsi memory verify` | 重算流水和对象的哈希，与每份库外登记报告核对运行号、批次末序号和末行哈希；区分缺报告的完整提交、缺批次或哈希不符的损坏。按哈希名检查原件还在不在。只报告，不改库 |
| `rsi memory backfill [运行编号…]` | 用已有的任务运行记录登记。不给编号时，按先后处理所有满足 5.4 条件、还没登记过的任务运行，和每次任务运行开始前自动做的一样 |
| `rsi memory show <编号>` | 打印一个对象和它的交付 |
| `rsi task <编号> --memory none` | 这次运行不给记忆，也不登记 |

`rsi init` 建立空的库。`rsi status` 加一行：记忆版本、条数、还有几次运行没登记。`rsi rollback` 不动库。这些命令和别的命令一样，同一时间只运行一个。

**检查。** `rsi check` 加这些项，都不调用模型：

- Lab 的命令在任务和试跑两套权限下，读不了也写不了 `memory/`（库）；
- Meta 的命令能读库，写不了；
- `memory` 工具服务经过合成后的启动方式，读得到工作区里的快照，读不到库，连不上网；
- 文献工具服务的那套收窄过的权限同样碰不到库；
- 让 Codex 用假模型端点真的调用一次 `memory` 工具服务的工具，确认它被发现并且返回正常。

### 5.8 Meta 能改什么、不能改什么

| | Meta |
| --- | --- |
| 库的内容、对象的写法、登记的规则、快照里放什么 | 不能改。它们在控制程序里，库对它只读 |
| `tools/memory/` 的代码、技能、Lab 的指示、`literature` 角色怎么用记忆 | 可以在候选版里改，照常试跑、自己决定发布 |
| 在设置里去掉 `memory` 工具服务 | 可以。Lab 就不再用记忆；登记照常进行，因为登记不依赖工作区 |

design.md 里 Meta 碰不到的四样东西不变，库归在“已有的运行记录”这一样里。Meta 自己的经验（哪次改动试跑结果如何）仍然在 `records/` 和 `meta/notes/` 里，不进这个库。

**给 Meta 的说明。** 控制程序的每轮提示说明主库只读，指出文献回执、Lab 提议和所有者事件的登记报告位置。Meta 可以调整 Lab 的记忆工具、技能和指示。具名试跑在容量裁剪前排除本任务交付、自身的解释和依赖这些修订的对象。Meta 可从调用记录核对启动条件、台账版本及快照指纹。

### 5.9 第二步的契约

第二步让 Lab 把判断、决定、调查、做法经验和子问题提议进库。下列约定由[第二阶段实施与验收记录](plan-memory-proposals.md)细化，首个交付是一条可追溯、可在后续任务取回的判断。

- **怎么提。** `memory` 工具服务加一个提议的工具。它只检查格式，把提议写进工作区的 `.tmp/` 里，告诉 Lab：已记下，运行结束后才核对，现在还不在记忆里。
- **谁来核对。** 运行结束、工作区封存后，控制程序从封存的那份里读提议。读法和收文献日志一样：只读有大小上限的普通文件。
- **格式。** 用上游的那一组字段：种类、编号、预期的当前版本号、所属的问题、内容、引用的证据、引用的对象和关系。关系有四种：支持、挑战、背景、由此推出。内容有大小上限。每种对象有一个必填的文字栏。除了问题以外，都要写明适用范围；不知道的条件写成空，空不代表什么条件都适用。
- **能引用什么。** 每条引用都要给出本次运行的工具回执。新证据对照文献工具返回的文本；历史证据和对象同时对照 `memory` 回执与控制程序摆放时的快照，核对对象编号、修订和对应内容。工作区里的快照可以被 Lab 改写，控制程序以摆放时的可信内容为准。是否进一步核对模型可见的输出，留给第二步设计。
- **不能自己填的。** 支持情况、已验证的范围、新鲜度，Lab 不能写。登记时支持情况固定是“待核对”。
- **引文。** 提议里的引文必须在它引用的证据文本里原样出现。
- **版本。** 预期的版本号和库里当前的对不上，这条提议不登记。
- **不通过的。** 原因写进这次运行的登记报告。后续快照展示原因时也要按 5.5 排除来自被过滤任务或对象修订的信息。
- **新鲜度。** 引用的对象有了更新的版本、你标记过某个来源有变、原件不在了，这三种情况下，依赖它的对象在检索时标成待复核或不可用。标记来源有变、撤回一个对象，是你用的两个命令。
- **检索。** 判断连同它的支持和挑战证据一起给；待复核的和反证排在前面。
- **做法经验。** 记做了什么改动、为什么、结果是变好、变差、没变还是没跑成、在什么条件下。照 MolRSI 的修改记忆。

第一步的库要为这些留好位置：对象可以有多个版本，可以互相引用，快照的去除规则能沿着引用往下推（5.5）。

## 6. 考虑过的做法

| 做法 | 内容 | 取舍 |
| --- | --- | --- |
| 一、记在工作区里，Lab 自己读写 | 在 `work/` 下放一个记忆文件夹，加一个技能，Lab 在任务里直接写。最接近 MolRSI | 不选。写进去的内容没人核对；它和 Lab 的工作方式在同一条版本线上，Meta 能在候选版里改事实，回退版本时知识跟着退；试跑见过的任务时看得到上次的结论 |
| 二、单独一个库，只有控制程序能写（本文） | 上游的规矩，加 InfraRSI 的核对后写回 | 你选的。只有库在工作区之外，才守得住“试跑不被上次的结论影响”和“Meta 不能改事实”这两条 |
| 三、只做自动的证据台账 | 做法二里自动登记的那一半 | 作为做法二的第一步。它不依赖 Lab 配合，做完就能用旧记录回填；缺点是库里没有“当时得出了什么判断”，由第二步补上 |
| 直接搬上游的代码 | 把 `scientific_memory.py` 和它依赖的内核带过来 | 不选。它的每条规矩都靠内核担保，而 design.md 定了控制程序不接内核；带过来的代码会放在 Lab 能改的地方，担保就没有了 |

**M5 的通过条件**

- `rsi install-memory` 存出新版本，装第二遍不变；`rsi check` 通过；`rsi memory verify` 通过。
- 分别验收交付次数和去重后的段落数。按“完整交付次数 / 本轮不同段落数”统计，R0009 为 17 / 17，R0010 为 46 / 41，R0012 为 18 / 17，R0013 为 107 / 90。
- R0009 和 R0012 的 17 个不同段落全部重合。库中共用这 17 个段落对象，两轮的交付分别保留当时的文档编号作别名。
- 用 DOI `10.1093/bioinformatics/btp352` 查，能找到 R0009 和 R0012 的两次成功获取和那 17 个段落。两轮的 `search_papers` 均交回带该 DOI、PMID、PMCID 和来源编号的论文标识记录，可据此分别匹配两次获取时写的 `PMC2723002` 和 `europe_pmc:MED:19505943`。标识核验情况按各次获取的回执呈现：R0009 未报告，R0012 报告了 DOI、PMCID、PMID。
- R0010 引文清单里的 5 行、R0013 的 7 行，每一行都能在库里按文档编号和定位找到，并且引文在那段文本里原样出现。

**M6 怎么做。** 我起草一个接着 `paired-validation` 往下的任务，它需要用到 R0010、R0013 取过的那几篇方法论文，并且允许引用记忆里的段落。你看过任务文字以后：

1. 运行 `./rsi task <新任务> --no-meta --memory none`。从这次运行的 `call.json` 取 `version_before` 和 `tree` 作基线，里面已经包含启动前封存的人工改动。
2. 比较当前工作区版本的树和基线 `tree`。两者不同时执行 `./rsi rollback <第一轮的 version_before>`。第二轮启动前确认当前版本的树等于基线，期间不手动编辑工作区。
3. 运行 `./rsi task <新任务> --no-meta`，用第二轮 `call.json` 的 `tree` 再核一遍。两次实际起点有差异时，将对照标为无效。

**M6 的通过条件**

- 第二轮最终引文至少有一条能逐项对应本轮某次 `memory` 调用实际交回的回填段落。保留调用编号，核对证据编号和修订、文档编号和版本、原件哈希及定位，并检查引文在这次回执的该段文本中连续原样出现。若记忆只交回 A，最终却引用了从文献服务取到的 B，即使 B 也在库中，这条引文也不算匹配。
- 给出两轮的文献工具调用数、取全文和读原文次数、负责人线程 token 用量、时长和任务检查结果。最终引文按仅有记忆回执、仅有当轮文献回执、两者都有、无匹配回执分别计数。注明负责人 token 未含子线程，第二轮共用第一轮可写入的 `library/`。两次观测只用于验收复用流程。

## 10. 已知局限与以后

- **进了库不等于模型看过。** 见 5.4。实测的差距是 41 段里 1 段，但没有保证。
- **原件复核的覆盖有限。** 第一阶段在登记时核对原件哈希。现有 `tasks/lit-service/audit.py` 可独立重建部分 XML 引文。将独立复核结果写回库时，标注应指向接受复核的具体段落修订及其原件。
- **只覆盖文献工具服务。** Lab 用 Scite 连接器、网页搜索、pdf 技能读到的东西没有可以核对的原件，不登记。第二步里它们也不能当证据引用。
- **中断的运行不登记。** 它没有会话文件。要登记，得先让中断和恢复的那两条路也收会话文件。
- **被分页切开的段落不登记。** 要整段交回才算。
- **检索是词面匹配。** 换一种说法可能找不到。漏掉多少要单独量。
- **解析器的代码变了而版本号没变时**，同一个定位可能交回不同的文本。这时新的那次不登记，报告里单列，要你来看。
- **论文标识可能不全。** 如果快照里没有从查询的 DOI 连到某次获取的标识依据，这次获取只能按原请求标识或文档编号另查。共享同一个文件的多条记录可以并列展示。
- **Meta 自己写的小测试排除不了同任务内容。** 它没有任务编号。记录里写明。
- **`--memory none` 的运行不登记。** 所以对照里不给记忆的那一次取到的原文不会留在库里。
- **记忆不随版本回退。** 回退以后 Lab 的工作方式变旧了，记忆还是新的。
- **快照是整份复制。** 库大了以后要改成按需取。
- **判断的支持情况永远是“待核对”**，直到另外有了核对的机制。
- **以后可做。** 给交付补“模型看到了没有”的标注；重新解析原件的核对；页面图片；计算结果作为证据；让 Meta 在试跑请求里选记忆条件；按旧版本号给快照；和上游的库互相导入导出；新证据和旧判断的自动配对。

## 11. 审稿后改了什么（2026-11-20）

两轮审阅都对照了现有控制程序、文献服务和历史运行。下表列出影响实现或验收的改动。

| 原来的写法 | 问题 | 修订后的约定 |
| --- | --- | --- |
