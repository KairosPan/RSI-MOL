## 实施顺序

1. **先写离线验收。** 在临时安装中，以 R0016 的字段构造一条可通过的历史证据引用，再分别改动引文、文档别名、修订和启动快照。增加重试及中断场景，验证只产生一个批次和一份报告。旧记录和旧快照继续按原格式回放，R0015/R0016 审计应给出原结果。
2. **接通一条判断的完整流程。** 先实现上表五个环节。首个样例的所属问题由控制程序从该次启动时的任务目标生成，权威来源记为 `task_contract`，保留任务出处。首批引用已有段落，随后接入当轮新取得且已通过第一阶段核验的段落。对没有提议附件的历史运行继续沿用已有登记报告。
3. **扩充对象与检索。** 依次加入子问题、决定、调查、做法经验。引用固定到对象和修订，可记录支持、挑战、背景或推导关系。查询同时返回支持和挑战材料。加入预期修订冲突、同任务间接引用和容量不足的测试，再实现所有者标记来源变化及撤回对象的命令。所有者操作有独立身份和库外校验记录，新鲜度从可见依赖和原件状态计算。
4. **在现有安装上验收升级。** 在 V0009 副本验证升级、保留用户修改和重复安装。运行旧版回放、全量回归及 `rsi check`，覆盖正常任务、同任务试跑、空快照和主库隔离。用真实 Codex 配本机脚本化模型跑完“提交、下次取回、同任务试跑排除”后，再评估是否需要新的真实模型对照。

## 五类提议、来源变化与撤回

普通 live 任务通过 `propose_memory` 提交下表中的对象。每条提议都给出稳定的编号、所属问题和预期修订。只有创建该对象的任务能更新它。控制程序从任务目标生成根问题，Lab 也可以把提议归到本轮已取回的子问题。

| 种类 | 正文字段 | 编号前缀 |
| --- | --- | --- |
| 子问题 | `text` | `subquestion_` |
| 判断 | `statement`、`scope` | `judgment_` |
| 决定 | `decision`、`scope` | `decision_` |
| 调查 | `description`、`scope` | `investigation_` |
| 做法经验 | `change`、`rationale`、`outcome`、`scope` | `method_experience_` |

适用范围未知时填空字符串。做法经验的结果可以是 `improved`、`degraded`、`unchanged` 或 `failed`。除子问题外，至少要引用一处证据或一个对象。历史对象引用填在 `object_refs`，每项包含 `id`、`revision` 和 `relation`。控制程序用启动快照和提交前的原生工具回执核实对象内容、修订及读取顺序。证据引用继续使用 `source_refs`。

`recall_objects` 可按种类搜索，`get_evidence` 可按编号和修订精确读取。判断的结果包括支持与挑战材料，已有其他可见对象提出挑战时也给出其编号和修订。新快照优先展示待复核结果与挑战材料。科学支持状态仍为 `pending_review`。

所有者可以运行 `./rsi memory source-changed <原件SHA-256>` 或 `./rsi memory withdraw <对象编号> <修订号>`。新快照把来源变化和被引用修订已有新版的依赖标为 `needs_review`，把原件缺失或依赖已撤回修订的对象标为 `unavailable`。同一操作重复执行会返回原有登记报告。批次已提交而报告尚未落盘时，重试该命令或运行 `./rsi memory backfill` 可以补齐报告。手动工作区可用 `./rsi install-memory` 重新摆放快照。

端到端测试用真实 Codex 连接本机脚本化模型。第一个任务用本轮首次读到的段落提交判断并提出子问题，第二个任务取回两者，提交决定、调查和做法经验。第三个任务在来源变更后读到待复核标记和反证，在撤回后读到沿引用传递的不可用标记。对第一个任务试跑时，其判断和依赖该判断的其他任务对象均被排除。

```sh
PYTHONPATH=control python3 -B -m unittest tests.test_memory_objects_lifecycle tests.test_current_judgment_recovery
```
